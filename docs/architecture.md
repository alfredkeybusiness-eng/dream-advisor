# Architecture: event-driven retirement-intelligence OS

Target architecture, agreed after reviewing the initial Render/Postgres
backend (PR #2's first version — since replaced). The core critique that
drove this: signal collection, publishing, enrichment, outreach, and
reporting were mixed into one stream. That's brittle. The fix is
event-driven: signals enter once, get classified, then separate workers
decide whether to publish, enrich, outreach, or archive — so any one
stage (or vendor) can be replaced without rebuilding the rest.

```
AVINA (+ future: YUTORI)
        │
        ▼
 SIGNAL INGESTION
        │
        ▼
 VERIFY + DEDUPE
        │
   ┌────┴────┐
   ▼         ▼
CONTENT    CONTACT
ENGINE     ENGINE
   │         │
   ▼         ▼
CLOUDFLARE  ENRICHMENT
WEBSITE        │
               ▼
          EMAIL VALIDATE
               │
               ▼
          OUTREACH GATE
   │         │
   └────┬────┘
        ▼
  REPORTING LAYER
```

**Non-negotiable rule carried over from the spec**: publishing and
outreach are separate pipelines. A signal can be worth publishing with no
contact attached. A contact can exist without being outreach-eligible.
Only verified + validated + relevant contacts ever reach a sender.

## Stack decisions

| Layer | Choice | Why |
|---|---|---|
| System of record | **Cloudflare D1** | Already connected in this environment (no credentials to provision); native to the rest of the Cloudflare stack. Neon was the alternative but nothing is provisioned there and no connector exists here — Hyperdrive can front an external Neon instance later without a rewrite if that's still wanted. |
| Event bus / API | Cloudflare Workers | Per the original design. |
| Job queue | Cloudflare Queues | Per the original design — not yet built (see status below). |
| Generated assets | Cloudflare R2 | Per the original design — not yet built. |
| Public site | Cloudflare Workers + D1 | `site/` — see below. |
| Discovery sources | **Avina only, for now** | No Yutori connector exists in this environment. The architecture treats every source as just another producer onto `signal.discovered`, so adding Yutori later is additive, not a redesign. |

The Render + Postgres + FastAPI backend from the first version of PR #2
was **removed**, not kept alongside this — same job (serving structured
campaign data), redundant stack.

## What exists right now

- `db/` — local SuperDB lake, the interactive/agent-driven working store
  (see `db/README.md`). Separate from D1; nothing syncs them automatically.
- `.prime/agent/skills/` — Prime Agent's daily Avina-rotation task, the
  one piece of actual automation that exists today.
- `site/` — the public Cloudflare Worker + D1 site, tested locally,
  **not yet deployed to a public URL** (needs `CLOUDFLARE_API_TOKEN` /
  `CLOUDFLARE_ACCOUNT_ID` as repo secrets, or a manual `wrangler deploy`
  — see `site/README.md`).

## Suggested build order from here

1. Deploy `site/` (needs the two secrets — everything else is ready).
2. Event bus: a Worker + Queue that takes `signal.discovered` and runs
   normalize → verify → dedupe → classify → store, replacing the by-hand
   D1 inserts.
3. Wire Avina's `query_signals` output into that pipeline as the
   `signal.discovered` producer (the Prime Agent skill already knows how
   to call Avina — it becomes a producer instead of a direct-to-SuperDB
   writer).
4. Contact extraction + enrichment + email validation + outreach gate, as
   its own pipeline, per section 15-21 — deliberately after publishing
   works end-to-end, since the spec's own rule is that these stay
   separate.
5. Reporting layer, reading events rather than recomputing from
   scratch — per the original note.
